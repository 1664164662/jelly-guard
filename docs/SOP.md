# 试玩广告生产 SOP（Playable Ad SOP）

> 这份 SOP 不是理论模板，而是《果冻防线》实际跑过一遍的流程。  
> 目标：把一个「游戏卖点」在 2–5 天内变成可投放、可测试、可复用的 15–30 秒 H5 试玩。

## 0. 适用范围

- Hybrid casual / 休闲游戏的试玩广告
- 信息流、激励视频、插屏等需要「即点即玩」的场景
- 单文件 HTML，可在 MRAID / iframe / 广告平台容器内运行
- 有或没有美术资源都能启动：本项目的所有视觉由 Canvas 程序化绘制

## 1. 角色与职责

| 角色 | 本项目中的承担者 | 负责 |
| --- | --- | --- |
| 创意 / 策划 | 我 | Hook、30 秒节奏、教学、End Card 文案 |
| 技术美术 / 开发 | 我 + AI 辅助 | Canvas 渲染、交互、性能、构建 |
| 视觉 | 程序化图形 | 角色、炮台、背景、粒子、图标 |
| QA | 我 + 自动化脚本 | 真机、埋点、广告桥、尺寸、回归 |
| 投放 | 未接入真实投放 | 变体、UTM、指标口径 |

> 独立完成时，一个人可以承担多个角色，但**验收标准不能合并**：做的人不能只凭“我觉得可以”就发版。

## 3. 七步流程

### Step 1 · Brief（0.5 天）

必须写清楚 6 件事：

1. 游戏本体是什么品类，核心爽点是什么；
2. 试玩要证明哪一个爽点（只选一个）；
3. 目标人群和投放场景；
4. 时长（15 / 20 / 30 秒）和首帧限制；
5. 成功指标：完播率、CTA 点击率、安装转化，还是素材迭代速度；
6. 不能做什么：不能出现真实品牌、不能依赖网络、不能超过平台体积。

**验收**：一个没玩过游戏的人，读完 brief 能说出“玩家在试玩里要做什么”。

### Step 2 · Hook 发散（0.5 天）

- 用 `ai/prompts/01-concept.md` 让模型产出 10 个 Hook；
- 人工按「3 秒可理解 / 反馈密度 / 单手 / 可复用 / 制作成本」打分；
- 只保留 3 个进入灰盒，不要一上来做美术。

**本项目选择**：合成 + 塔防。理由：拖拽一次就能同时完成“操作”和“成长”，不需要教学文案。

### Step 3 · 灰盒与 30 秒节奏（1 天）

- 先用色块和圆点把核心循环跑通；
- 0–3 秒必须出现可点击的主按钮；
- 3–10 秒必须完成一次教学；
- 10–22 秒至少一次压力上升；
- 22–30 秒必须有高潮（Boss / 清场 / 加速）；
- End Card 只保留一个主动作。

**验收**：把手机给一个没看过的人，30 秒内能完成第一次合成，不需要口头解释。

### Step 4 · 视觉、音效与反馈（1–2 天）

优先级从高到低：

1. **可读性**：主体 / 背景 / 强调色三层分明；
2. **反馈**：合并、命中的粒子、音效、轻震；
3. **情绪**：Boss、糖爆、胜利的屏幕表现；
4. **装饰**：背景星点、光晕、环境粒子。

**约束**：不引入图片和字体；所有图形在 Canvas 里程序化生成或预渲染。这样体积、加载、版权都可控。

### Step 5 · 变体与 AI 流水线（0.5 天）

- 把主题色、文案、难度抽成 JSON；
- 用 schema 约束 LLM，只让它输出配置；
- 校验失败自动 fallback；
- 至少产出 2 个人工变体 + 1 个 AI 辅助变体，进入 A/B 池。

```bash
npm run ai:variant -- --brief "夏日柠檬气泡，清爽、轻快" --id lemon
npm run ai:variant -- --brief "..." --id lemon --offline --force
```

**验收**：改一个 JSON 并重新构建，不需要改游戏代码。

### Step 6 · 构建与 QA（0.5 天）

```bash
npm run build
npm run qa
npm test
```

必须通过：

- 单文件 ≤ 150 KB，gzip ≤ 50 KB；
- 0 个外部请求；
- 5 项浏览器冒烟测试；
- 3 个尺寸下无横向滚动 / 按钮出屏；
- CTA 只触发一次，且能正确调用广告桥；
- 页面隐藏再回来，计时器不跳变。

### Step 7 · 投放、复盘与迭代（持续）

- 每个变体带独立 `variant` 参数和事件标签；
- 先看**完播率 / 首次合成时间 / CTA 点击率**，再看安装；
- 每次只改一个变量：主题、首屏文案、Boss 时间、难度；
- 记录“哪个变体赢了、为什么”，而不是只记录 CTR。

> 本项目没有真实投放数据，所以文档里不编造 CTR。投放后的数据应该由真实平台回传，再回填到 `docs/CASE-STUDY.md`。

## 4. Definition of Done

- [ ] 30 秒内可完成一次完整试玩，无需刷新
- [ ] 首屏无加载态；点击开始后 200ms 内可操作
- [ ] 第一次合成可在 6.2 秒内通过主动操作或自动兜底完成
- [ ] 胜利和失败都能进入 End Card
- [ ] End Card CTA 至少尝试一种广告桥
- [ ] 关键事件可在父页面实时看到
- [ ] 单文件构建通过尺寸 / gzip / 外部请求检查
- [ ] 三种尺寸真机或模拟器通过
- [ ] 没有 console error
- [ ] AI 生成的变体经过 schema 校验，且保留运行记录

## 5. 常见失败模式

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 玩家不知道拖哪里 | 只有文字，没有空间指引 | 虚线路径 + 同色槽高亮 + 光标 |
| 第一次合成太晚 | 教学依赖玩家自己探索 | 6.2 秒自动兜底 |
| 合并后反而输 | 炮台只覆盖单列，资源集中后漏穿 | 同轨优先 + 跨轨兜底 |
| 结算页卡顿 | `backdrop-filter` 叠在持续重绘 Canvas 上 | 结束页停 Canvas，切静态背景 |
| 包体超标 | 引入图片 / 字体 / 框架 | 程序化绘制 + 单文件内联 |
| AI 输出不可用 | 让模型直接写代码 / 无 schema | 只生成配置，代码做校验和回退 |
